worker ループを **1 周だけ** 実行する。`/loop` が本コマンドを反復して呼ぶ。

あなたは**実装役**である。マージしない。`@codex review` を要求しない。
どちらも master の役割で、判定の独立性のために分けてある。

**これは入口である。** **ステップ 2 以降は本体（`loop/procedure/worker.md`）にある**
——**cron が運ぶのは入口だけ**なので、**ここに書き足すほど、手順書を直したときに
走っているセッションが捨てる周回が増える**（#319。理由は `bin/loop-procedure-body` の冒頭）。
**ステップ 1 が残っているのは、本体を読む前に走るから**である（1.2）。

## 絶対ルール

> **`gh pr merge` を実行してはならない。** ゲートを持たない側がマージすると、
> 分けた意味が無くなる。

`main` へ直接 push しない。`AGENTS.md` の規約に従う（特にテストファーストとレイヤ境界）。

## 1. 停止条件

`loop/STOP` が存在するなら、**何もせず直ちに停止する。**

### 1.0 同じ作業場の周回が走っていないか確かめる

**直列化する単位は「作業場」であって「役」ではない**ので、**worker は何人いてもよい**
（別の作業場で走る worker とは重ならない）。**冒頭で決着させる**——途中まで進んでから
気づくと、`ready` を取った状態で止まることになる。

```bash
bin/loop-lease acquire worker "<この手順書の冒頭にある `版:` の値>"   # token を控える
```

- **exit 0** → 続ける。**この周回を終えるとき（何もせず終わる場合も含めて）必ず返す**

  ```bash
  bin/loop-lease release worker "<token>"
  ```

- **exit 1** → 走っている周回がある。**何もせず終わる。待たない**——
  走っている側が同じ状態を読むので、待っても同じ結論にしかならない
- **exit 2** → 設定か環境の誤り。標準エラーに出た内容を報告して終わる

**取れなかったことを黙って飲み込まない。** 何周も取れないなら、
**返し忘れた周回がある**（期限が切れれば自動で引き継がれるが、それまで動かない）。

**印がずれていたら、`acquire` は exit 3 で止まる** (#241 / #243 / #244 のレビュー)。
**exit 2（設定か環境の誤り）とは行き先が違う**ので、**番号で分ける**——
**文言で見分けない。**
**配られた手順書がディスクより古い**ということなので、**この周回は捨てて呼び直す**
（**1 回だけ**。**lease は取れていないので返さない**）。

**その前に、印を持つ木がここにあるかを見る** (#262)。
**その印が自分の open PR のものなら、その枝へ入ってから取り直す。**
**木を触る前に、作業場を原子的に押さえる**——**読むだけの確認では足りない。**

```bash
bin/loop-lease recover worker "<読んだ印>"    # token を控える
```

- **exit 0** → 押さえた。下へ進む。**この先どの経路で終わるときも必ず返す**
- **exit 1** → 走っている周回がある。**何もせず終わる**
- **exit 3** → 印は揃っている。**回復の出番ではない**ので、下（捨てて呼び直す）へ進む
- **exit 2** → 判定できない。標準エラーに出た内容を報告して終わる

```bash
bin/loop-claim pr <PR番号>                    # **編集する前に取る** (#203)
case "$?" in                                  # **受けなければ、錠は掛からない**
  0) ;;                                       # 取れた
  *) bin/loop-lease release worker "<token>"; exit ;;   # 別の作業場 / 判定できない
esac
gh pr checkout --detach <PR番号>
bin/loop-procedure-stamp worker "<読んだ印>"  # 揃ったか。判定はここ 1 箇所が持つ
```

- **exit 0** → 揃った。**この周回はその PR の作業として続ける**（本体のステップ 3）
  ——**本体はその枝で読む**（1.2 と同じ口。**枝の上で揃っているのはこの道だけ**である）
- **それ以外** → `bin/loop-lease release worker "<token>"` して終わる

**押さえたことは、進んでよいという意味ではない。** **素通りにしない**ためで、
**その枝なら手順書もスクリプトも揃う**から通るだけである——**揃わなければ返して終わる。**

**この周回は 1.1 で `origin/main` へ移らない**——**`bin/loop-sync-main --fetch-only` を使う**
（**移すと、いま入ったばかりの枝から出る**）。**比較先は自分で埋める**
（**`--fetch-only` は SHA を出さない**ので `after="$(git rev-parse HEAD)"` と書く）。

**ここで `bin/loop-stall --reset` を呼ばない。** **消すと、次の周回が積んだぶんも
一緒に消える**——**毎周回 1 に戻り、3 周へ永久に届かない。**

**呼び直しても同じなら、そこで終える**——**`bin/loop-stall procedure-stale` を通す**。
**積むのは 2 回目だけ**（**1 回目でも積むと、1 件の配り間違いが 2 つ数えられる**）。

### 1.1 `origin/main` の先端へ移る

作業ツリーが clean であることを確認する。dirty なら、前の周回が中断している。
`bin/loop-stall dirty` を通して停止し、何が残っているかを報告する。

**ブランチとして `main` を掴まない** (#196)。**detached でよい** (#102)——
**worker はどこでもブランチを掴まず**、**ブランチ名は push とブランチの更新でだけ使う。**

```bash
before="$(git rev-parse HEAD)"
if ! after="$(bin/loop-sync-main)"; then
  bin/loop-stall main-sync-failed
  exit
fi
bin/loop-procedure-changed --role worker "$before" "$after"
```

**`exit 1` だけが「続けてよい」**（**1 以外はすべて捨てる**。master と同じ扱い）——
**`exit 2` だけを並べない。** **判定器そのものが消えた・実行できない（126 / 127）ときは
どの分岐にも入らず**、**「判定不能なら捨てる」が成立しなくなる。**

**捨てるときは、この順で行う。**

```bash
bin/loop-stall --reset main-sync-failed
bin/loop-lease release worker "<token>"
# ここで /loop-worker を呼び直す
```

**消してから返す。** **返してから消すと、間に入った周回が消える前のカウンタを読む。**
**消すのは、同期の失敗のぶんだけ** (#266)——**全部消すと、呼び直した先が印ずれで
積んだぶんまで次の周回が消し**、**同じ障害が何周続いても人が呼ばれない。**

**`--reset` が落ちても、周回は止めない** (#270)。
**標準エラーに出た内容を報告して、そのまま先へ進む**——**言うことと、止めることは別**である。

**握ったまま呼び直さない。** **呼び直された周回が 1.0 で自分自身に阻まれ**
（`acquire` が exit 1）、**結局、次の cron まで動かない。**

**呼び直しは 1 回だけ。** **呼び直した先で再び打ち切りになったら、そこで終える。**
**ただし、新しい版が読み込まれる保証は無い**——**同じセッションで既に読み込まれていると
「instructions unchanged」と返り、古い版のまま走る**（実測で 2 回中 1 回。#94）。
**届かなかったことを検出する手立ては無い**（**呼び直した回は `before == after` になる**）。
**それでも呼び直す**——**cron や人の起動で始まる周回には最新が届いている**ので、
**遅くともそこで最新に戻る。**

**`bin/loop-sync-main: No such file or directory` と言われたら、それが版ずれである。**
**症状はファイルが無いことだが、原因は「手順書のほうが新しい」**——
**`git switch --detach origin/main` で版を揃えてから呼び直す。**

**やり直すかどうかは、回数ではなく理由で決まる** (#217)。**判断はスクリプトが持つ**
ので、ここに条件を書き写さない（一覧の正は `bin/loop-sync-main` の `RETRYABLE_REASONS`）。
**規則が現実に合っていないと感じたら、破るのではなく直す。**

どれかに失敗したら `bin/loop-stall main-sync-failed` を通して停止する。

### 1.2 本体をディスクから読む

**この手順書は入口である。** **ステップ 2 以降（「周回の出口」を含む）はここには無い。**

```bash
bin/loop-procedure-body worker
```

- **exit 0** → 出力が本体である。**この周回は、入口と本体を続けて 1 つの手順として読む**
- **それ以外** → `bin/loop-lease release worker "<token>"` して終わる。
  **入口だけで進まない**——**手順の大半が無いまま走ると、レビュー対応も出口も飛ばす**
  （**止まったほうが軽い**）

**読むのは同期のあとである** (#323 のレビュー)。**前に置くと、その周回が始まった時点の
作業ツリーから読む**——**未マージの PR の枝に居た周回は、その PR の本体をそのまま実行する。**
**`bin/loop-procedure-changed` は見つけられない**（**`BEFORE` の側にしか無い変更は
意図して除いてある**。#259）ので、**レビューを通っていない手順が黙って走る。**

**出られなくなる形もある。** **`bin/loop-procedure-body` を持たない古い checkout に
居ると、同期の前に読もうとして落ち**、**同期へ到達しないまま毎周回そこで止まる**
——**直しに行く経路が、直る前の状態に閉じ込められる**（#184 / #262 と同じ形）。

**印がずれて枝へ入った周回だけは、その枝で読む**（1.0）——**あそこは
`bin/loop-procedure-stamp` が「手順書もスクリプトも枝で揃っている」ことを確かめている。**

**なぜ分かれているかは `bin/loop-procedure-body` の冒頭にある** (#319)。
**検出はそのまま残す** (#241 / #243)——**入口が変わったときは、これまでどおり鳴る。**

## ステップ 2 以降

**本体にある**（ステップ 1.2 で読んだもの）。**ここには写しを置かない**——
**直す先が 2 つになり、cron が運ぶ本文も元の長さに戻る。**

- **2. やることを決める** — **届いた指示・自分の PR・再開する作業を見る**
- **3. レビュー指摘に対応する**
- **4. `ready` から 1 件を取って実装する**
- **周回の出口** — **何もしなかった周回もここを通す**
- **5. 空転を検出する**
